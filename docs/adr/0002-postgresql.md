# 0002: PostgreSQL as the source of truth

Status: accepted, 2026-10-10

## Context

The data is relational: users have appointments, records and prescriptions, and payments must be
transactional. The current Firebase Realtime Database stores appointments twice (once under the patient,
once under the doctor) with no transaction, so the two copies can drift apart, and IDs come from
`Date.now()`, which can collide.

## Decision

- PostgreSQL 17 holds all durable data. MongoDB is not used.
- Redis is added later for caching and rate limiting only, never as the source of truth.
- core-api uses Prisma (Prisma 7, node-postgres driver adapter) and versioned SQL migrations.
- Primary keys are UUIDs generated by the database (`gen_random_uuid()`).
- Emails use `citext`, so `A@x.com` and `a@x.com` are the same account.
- Double booking is prevented by the database: a partial unique index on `(doctor_id, scheduled_at)` for
  `pending` and `confirmed` appointments. Cancelled and completed rows do not block a slot.
- Money is stored as integer minor units (paise/cents), never as a float.

Two of these rules cannot be written in Prisma's schema language (the `citext` extension and the partial
index). They are hand-written SQL inside the init migration and are covered by tests that run against a real
PostgreSQL.

## Consequences

- Tests that touch these rules need a real database (local Docker, or the Postgres service in CI).
- Migrations are plain SQL files that are reviewed like code. Edit a migration that has already been applied
  and Prisma will refuse to continue; add a new migration instead.
- Each service gets its own database and role, so a later split (for example managed Postgres per service)
  needs no data untangling.
